# Test like a QA engineer — designed, proven, never twice

Several people build this app with their own Claude, and others record tests in QA Hub. QA Hub is the one shared place: each module has **behaviours** (what a user can do there), each behaviour should be **proven** by a test whose code really checks it, and there is **one test per behaviour**. The person may not be technical: they read your tests as plain steps with expected results.

The person may only say "automate this", "test the training page" or "I want negative tests for the forms". Take it from there: you design, write, push, run and fix — they read plain steps and results. When they ask for a kind of testing, map it onto QA Hub's types (functional, negative, boundary, validation, permission, workflow, smoke). QA Hub runs end-to-end browser tests only: for load, security scanning, API-only or unit tests, say so plainly and offer the browser tests that come closest — never pretend.

1. **Connect.** `qahub_status` (key, plan, whether their computer is connected, environments). Not linked: ask which project, `qahub_link`.
2. **Know the project.** Not mapped yet (`qahub_gaps` says so)? Map it yourself first — `qahub_map` with the whole module list made from `qahub_knowledge`'s pages; never ask the user to press a button for it. `qahub_project`: modules, their behaviours and state, sets, every test (steps, author, type, whether it's proven), spec folders, helpers. `qahub_gaps` first if there are change or fix requests — they come first (step 9).
   - **Know the app's code — read once for the whole team.** `qahub_knowledge` first — each page has its own topic, `page /its-address`, made from the code: what a user sees, the validation with its exact limits and error messages (your variables' rules and your negative tests' expected messages), the server calls and the files behind it: what a Claude already learned (pages and their source files, fields and their rules, messages, roles, flows). Use it instead of reading the code. A topic you need that's missing or **OUT OF DATE**: read just those files — here, if this folder has the app's code, else with `qahub_code` (from the project's GitHub) — then `qahub_learn` it — facts a tester needs, the files you read and the commit (`git rev-parse HEAD`) — so no teammate's Claude reads them again. If this folder has a Graphify report (`GRAPH_REPORT.md`, made by `/graphify .`), save its summary once as the topic `code map` — which files hold which parts of the app — and refresh it when `qahub_knowledge` says it's out of date.
3. **Design the module you're working on.** `qahub_design { module }`:
   - its behaviours: **untested** and **weak** first, high priority first;
   - the guide for each kind (create, edit, delete, search, validation, workflow, permission, calculation…) — what a professional checks, and what QA Hub requires the code to prove.
   - **A part of the app QA Hub doesn't have yet** (a page you just built): design and plan answer "no module". Add it first — `qahub_push { modules: [{ name, path: "/its-url", parent }] }` (parent only for a sub-page), nothing else in that push — then design it.
   - Not designed yet, or the feature adds something new → propose behaviours: one per thing a user can do ("Create a quote", "Delete a quote", "Only managers approve"), with kind and priority (money, data loss, access → high).
4. **Plan test cases, the way a QA engineer would — not only the happy path.** For each behaviour, using the guide:
   - **positive**: the main path, with every value read back after reopening;
   - **negative / validation**: required fields empty, wrong formats, duplicates → the message, and nothing saved;
   - **boundaries**: 0, the maximum, one more than the maximum;
   - **edit**: changed fields show the new values and unchanged ones keep theirs;
   - **delete**: gone from the list, from search and its page;
   - **workflow / permission**: every allowed move or role, and every forbidden one blocked;
   - **the whole life of a record** — see **The test standard** below: Create → View → Edit → Delete as a chain of tests, with every field.
   Each test case: a title, its type, priority, what must be true before it starts, and **every step with its expected result**. Check `qahub_find` for each — a **SAME** test already exists: improve it, never write a second one.
5. **`qahub_plan`** the behaviours and test cases. A test case whose title is already a test in that module updates that test (the reply lists it under "already tests") — change its code, never write a second one; `distinctFrom` never applies to the same title. High-priority and risky test cases (deleting, permissions, money) wait for a person by default — they decide what "correct" is; the reply says which wait: tell the user (with the link) and **stop** for those tests. Write the code for the approved ones.
6. **Look, then write the code.** `qahub_look { path }` every page the test touches first — the real role and name of each control, where it lands, the app's errors; never guess a selector from the code alone. No code for this part of the app? Design from what `qahub_look` shows. But the page shows what the app does *now*, not what is *correct*: expected results come from the plan and the person, never copied off a page that may be wrong. Then write it (`@playwright/test`, in the project's spec folders, reusing its helpers; `qahub_pull` first if you change a shared file) by the **Checklist** at the end of this skill. Also:
   - **a file to upload** (a photo, a PDF, a spreadsheet, a CSV): put it in the spec folder (e.g. `tests/fixtures/robot.png`), attach it with `setInputFiles(path.join(__dirname, "fixtures/robot.png"))`, and push it with the test. QA Hub stores it (up to 10 MB) and puts it next to the test on every run. A small made-up file, never a real person's document;
   - **who it runs as**: qahub_project lists the test accounts (names, roles, places). A permission test runs as the role that should — or shouldn't — be allowed; everything else as the default (leave `runAs` out). Two users of one role (customer A messages customer B): two accounts, `customer` and `customer-2`. A flow across roles, one person after another: take `qahub` from the fixtures and `await qahub.signInAs(page, "<name>")`, the name written out. **Two people at the same time** (one sends, the other sees it arrive; an admin changes what a user is looking at): `const manager = await qahub.as("manager")` — a second page, already signed in, open next to `page`; drive both, and check each one sees what the other did. Never invent an account or type an account's email; if the role a test needs has no account, skip that test and tell the user which role to add in QA Hub → Settings → Test accounts;
   - **dynamic test data — different every run, to find bugs one fixed value never hits**: every value a test types whose exact text doesn't decide what it proves (a title, a name, an email, an amount, a date, a note) comes from QA Hub and is linked to a **variable**, so each run — and each try of `repeat` — types something new. In the code: `const data = JSON.parse(process.env.QAHUB_DATA ?? "{}");` then `data.course_title ?? "QA Fire safety basics"` (the default keeps it runnable on its own). In the push: `data: [{ name: "course_title", value: "QA Fire safety basics", variable: "course_title" }]`. Reuse a variable from qahub_project → Variables when it fits; otherwise send it in the same push, `variables: [{ name: "course_title", kind: "text", rules: { minLength: 3, maxLength: 60, letters: true, spaces: true }, tricky: "sometimes" }]` — rules are what the field ACCEPTS (read its limits in the app's code or its validation message), so every drawn value is valid input; `tricky: "sometimes"` (an edge value now and then: longest/shortest allowed, accents, `O'Brien & <Co>`, other scripts, min/max/0) for the fields where that finds bugs — free text, names, amounts. A list (`kind: "list"`, real options) for a value that must be one of a set — with `pick: "round"`, so runs go through every option one by one (each one gets tested, none twice in a row), unless the order truly mustn't matter. Keep a value fixed (no variable) only when the test is ABOUT that value — a boundary or validation test types its exact edge case; a permission test, its exact role. Checks use the drawn value, never a copy: `await expect(row).toContainText(data.course_title)`. A name the cleanup finds must stay unique: add a short suffix in the code (`` `${data.course_title} ${Date.now().toString(36)}` ``) and leave room for it in the variable's maxLength. A person's choice wins: a value they made fixed ("fixed by a person") or linked elsewhere stays as they set it — don't fight it in your pushes;
   - **leave nothing behind — a hard rule**: tests run again and again, often on a server people work in, so every record a test makes is deleted by that same test. Name it uniquely (`` `QA course ${Date.now()}` `` — people can spot it, and the cleanup deletes exactly its own), and delete it in `finally { }` or `test.afterEach`, so it goes even when a check fails before the end (a failing check still fails the test; `finally` doesn't hide it). The delete is part of the flow: check it's gone. The app can't delete that thing? Tell the user before writing the test — every run will add one — and ask how to clean up. A push that creates without a guaranteed delete comes back with `leaves-data` / `cleanup-not-guaranteed`: fix it in the same turn.
7. **`qahub_push`** the files with each test's `type`, `priority`, `preconditions`, `covers` and steps `{ title, expect }`. **List the tests in the order a person would do them** (create → open → edit → delete) — that's the order they get their numbers and join a set (`sets`). A test is independent by default and every test runs even when another fails — so a record's life is ONE test that makes and deletes it, not a chain (a chain that stops halfway leaves its record behind). Only when a test truly uses what another one makes, give it `needs: ["<that test's title or ref>"]` — QA Hub then runs it after that test (in every run and every set) and skips it only if that test fails. Read the reply:
   - **a depth refusal** ("the edited value is never checked after reopening") → fix the test so it proves it. `waiver` only with a true reason the code can't prove it (shown in QA Hub; the behaviour then never reads proven) — never to get past a refusal you could fix;
   - **looks like TEST-…** → a duplicate: improve that one, or `distinctFrom` if it truly tests something else;
   - **would remove TEST-…** → `qahub_pull`, keep the teammate's test, push again;
   - **module isn't in QA Hub / covers something that isn't a behaviour** → use QA Hub's names, or add them (`modules`, `behaviours`);
   - **waiting for review** → stop; a person approves the plan first.
8. **`qahub_run { tests: [refs], repeat: 2 }`** on their computer — a new or changed test only counts (proven) once it has passed twice since its code changed. Failures name the test, step and error and whether the app broke or the page changed: fix the app if it's wrong, the test if it no longer matches — never check less or wait longer. **Find out, don't guess:** a step that waited for something that never came means the step before it didn't do what you thought — read where it ended, the page and the screenshot QA Hub returns, then the app's code for that click or save (a redirect, a dialog, a draft that opens elsewhere, a permission) before you change a line. Anything the test created before failing: make sure `finally` removed it, and tell the user if a failed try left something behind. Tries of a test that hasn't passed yet stay out of Results — run as often as you need. Push, run again — **keep going on your own until every test you're building has passed twice**: approved plans get written, failures get fixed, plans still in review get waited for (qahub_wait_review). Don't stop to report each round; QA Hub sends you back if you stop with work left. Stop only when you truly need the person (a missing test account, a real bug in the app, a decision only they can make): start that message with “Needs you:” and say what. A test that passes and fails by turns: `qahub_run { tests: [ref], repeat: 5 }` shows how often ("Failed 2 of 5 times") — find what makes it unreliable. A test with dynamic data gets new values on every try, so `repeat: 5` also hunts for data bugs: "Failed 1 of 5 times with different test data each time" comes with the values that broke it — try those values in the app; if the app is wrong (it should have taken them), that's an app bug to fix or report, never a reason to narrow the variable's rules. Not connected: an app on the internet can run on QA Hub's own test computers (`qahub_run { …, where: "server" }`); otherwise tell them once how to connect (QA Hub → Computers) and say the tests are sent, not run.
9. **Change and fix requests** (`qahub_gaps`): a change request on a **planned** test case is a person's note on your plan — `qahub_plan` it again with the change; on a test with code, change the code and push with `applied: true` (`replaces` when its title or file changed). A **fix request** (a person pressed "Ask Claude to fix it"; the session start says so): ask the user once before changing code. Then `qahub_fixes` — the step, the error and the screenshot of the moment it failed; look at the screenshot. Decide in plain words whose fault it is: the app (a bug — fix the app's code) or the test (the app changed on purpose — update the test and push it). Never make it pass by checking less or waiting longer. Then `qahub_fix_note { test, kind: "app" | "test" | "neither", note }` — one or two sentences a non-programmer understands, shown in QA Hub — and `qahub_run { tests: [ref] }`; a pass marks it fixed. Can't fix it after 3 rounds: `kind: "neither"` and say what a person should look at.
10. **Tell the user** in two lines: what is now proven (behaviours), what's still untested, the run result and its link.
11. **Suggest what's next — unasked.** From the untested and weak behaviours (`qahub_gaps`), recommend the 2–3 tests worth most, each with one plain reason — money, deleting data and who-may-do-what first ("Delete a course: nothing proves a deleted course is really gone"). Also suggest kinds they haven't asked for when the feature calls for them (a form with no negative tests, an approval with no permission test). Offer to do them; don't start without a yes.

## The test standard — what a client (technical or not) expects to see

Shallow tests are the failure here: a create test that fills only the required fields and checks two of them, then deletes, proves almost nothing. Before you plan, write two lists for each form or record (from `qahub_knowledge`, `qahub_code`, `qahub_look`):
- **Fields:** every field — required AND optional — with its type, limits, allowed values and messages. Optional fields are where bugs hide: fill them.
- **Where it shows:** every place a saved value appears afterwards — the list or card, search, the details page or drawer, the reopened form, exports (a PDF, a CSV, an email), other pages that use it (a dashboard count, a dropdown elsewhere).

Then plan by the kind of feature:
- **A record people create** (an SDS, a company, a user) — a chain of tests, each one thing a person checks, run in order with `needs`:
  1. **Create it with every field** — required and optional, values from variables; `qahub.keep("<thing>", { name, id })` at the end.
  2. **View it everywhere** — `qahub.take("<thing>")`; every field in every place on the "where it shows" list.
  3. **Edit every editable field** — then see each change everywhere it shows, and the unchanged fields kept.
  4. **Delete it through the screen** (the button or menu a person uses) — gone from the list, search and its page.
  Each test in the chain, when it fails, deletes the record itself (`finally`, when it didn't finish) so nothing is left behind; the next ones are skipped. Plus their own tests: required fields, limits (max, max+1), wrong formats, duplicates, who may do it.
- **A form alone:** each required field empty, each limit, wrong formats → the exact message AND nothing saved.
- **A list:** search, each filter, sorting, paging, the empty state.
- **A multi-step flow:** each step, going back, leaving halfway and coming back, the final result (the generated file's content, not only its link).
- **Import / export:** a good file, a bad file, and what came out.
Never take a shortcut through the app's API, a database or `page.evaluate` when the screen can do it — a test of a person's flow uses the person's screen. The API is only for cleaning up after a failure.

**The plan, as the person reads it:** one plain sentence per test saying what it proves ("Creating an SDS with every detail filled in saves all of them"), grouped by feature; its type and priority after it for those who want them. No jargon in the sentence.

**Before every push, review each test like a strict QA lead:** does it fill every field on the list? Check every place on the "where it shows" list? Would it catch a field that silently isn't saved? Uses the screen, not the API? If not, fix it first.

## Checklist for every test file
1. Tests start signed in as their test account: choose it by ROLE (qahub_project → Test accounts) and push it as `runAs`; cross roles with `await qahub.signInAs(page, "manager")`; two people at once with `const manager = await qahub.as("manager")`. No account for the role? Tell the user to add it. No log-in steps; never a password, key or token in a file.
2. Find elements the way a person does (qahub_look shows their names): getByRole with its name, getByLabel, getByTestId. No CSS classes or generated ids. Two of a kind (two searches, two "New" buttons): scope to the page's own region (main, the dialog, the row) — never first()/nth().
3. End every test with an expect of what the user should see; know what bug it would catch. A negative test must reach its rule (the other fields valid).
4. Prove it: a create or edit test reopens the record (reload, or open it by name) and expects the typed values; a delete expects that item gone; validation expects the message AND that nothing was saved. "No error" is not proof — QA Hub reads the code and refuses a test that doesn't prove it.
5. Never weaken a test to get green: no try/catch or .catch() on expect, no if (…isVisible()) before a check, no skip/fixme, no removed checks (helpers too), no force, no fixed waits — wait for what you expect. During a fix QA Hub refuses these.
6. Change the page only as a user does (click, fill, press) — no page.evaluate edits.
7. Each test stands alone, in a fresh browser, in any order: it creates what it needs, with unique values (e.g. Date.now()). Only if it really uses what another test makes: push it with needs: [that test].
8. page.goto("/path") — never localhost. Import only @playwright/test, Node's modules and your pushed files.
9. test("…") named exactly as planned; each step in test.step("Plain words") named exactly as its planned step — those are what people read.
10. One test per behaviour across the team: qahub_find first; a SAME test is improved, never written twice.
11. Leave nothing behind: whatever the test creates (unique name, e.g. `QA course ${Date.now()}`), it deletes in finally { } or test.afterEach — even when a check fails — and expects it gone. Can't be deleted in the app? Tell the user first.
12. Typed titles, names, emails, amounts, dates: QAHUB_DATA linked to a variable; expect the drawn value.
Then qahub_push the file (and helpers), qahub_run { tests, repeat: 2 }, and fix what fails.
